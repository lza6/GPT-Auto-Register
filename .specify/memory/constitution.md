# GPT 自动注册 · 项目宪法 (Constitution)

> 依据 GitHub Spec-Kit 建立。本文档是**所有开发决策的最高准则**，任何新增/修改/重构都必须与之对齐。

## 一、核心价值观 (Core Principles)

### I. 真实落地优先
禁止伪实现、占位逻辑、mock 假闭环。代码必须真实可运行、可调用、可验证。没有验证证据不得宣称完成。

### II. 生产可用
本项目已在生产部署。每次变更默认面向"真实用户 / 真实调用方 / 真实部署者"，而非演示。必须覆盖：空态/加载/错误/重试/防重复点击。

### III. 增量迭代，拒绝重构
只改必须改的；不推翻没坏的东西；复用已有轮子。禁止为了"更优雅"重写工作正常的模块。

### IV. 先思考后编码
任何代码前先做逻辑推演、依赖分析、多角度验证。强制在 `<thinking>` 内完成推理再动手。

### V. 证据驱动
启动/构建/接口/页面/测试/脚本/文档步骤，凡可验证必验证。外部受限项（付费 API/第三方凭证）必须写清：已做到哪步、缺什么、如何降级。

## 二、技术原则 (Technical Principles)

### 架构
- **分层清晰**：`api/`(路由) → `services/`(业务) → `services/db.py`(数据)，禁止跨层直连数据库。
- **协议优先、浏览器兜底**：注册主链路 `protocol_register` → `browser_register`，风控类失败不降级（避免限流）。
- **选择器集中**：页面选择器只改 `services/browser_selectors.py`，禁止散落硬编码。
- **配置收敛**：可调参数进 `config.json` / `config.example.json`，禁止魔法数字。

### 代码质量
- 函数 < 50 行，文件 < 800 行；命名表意，禁止 `data/temp/result/df` 类懒惰命名。
- 显式错误处理：禁止裸 `except:` 吞错；禁止静默失败。
- 数据库访问统一走 `db_session()` contextmanager，禁止手写 connect/close 样板。

### 性能
- 批量操作避免 O(N²)；导出/刷新支持并发（Semaphore 限流）。
- 前端轮询降载：日志增量、页面隐藏暂停、注册记录仅在任务运行时刷新。

### 安全
- `auth_enforced=true` 时占位符密钥必须 fail-fast。
- 凭据环境化（`CHATGPT2API_ADMIN_KEY` 等），源码禁止明文账密。
- 敏感配置脱敏；设置接口走白名单；清空接口需服务端 `confirm` + 自动备份。

## 三、测试标准 (Testing Standards)

- 覆盖率目标 ≥70%（核心路径 ≥85%），TDD 优先。
- 每个新增 API 覆盖 成功/失败/鉴权 三态。
- 每个新增配置项覆盖 默认 / 字符串'true'/'false' / 布尔 三态解析。
- 数据库迁移用 `ALTER TABLE` 兼容旧库，须有迁移测试。

## 四、决策框架 (Decision Framework)

做任何技术决策时依次自问：
1. 是否让"一次调用就跑通"更近？是否真的闭环前后端 / 调用 / 部署？
2. 是否符合核心价值（真实 / 生产 / 增量）？
3. 是否被测试覆盖、有验证证据？
4. 长期维护成本 vs 短期收益？
5. 外部资源受限时，是否写了降级与边界披露？

## 五、治理与变更 (Governance)

- 宪法高于一切既有实践；修订需记录在案并附迁移说明。
- 所有提交须通过：pytest 全绿 + 覆盖率不降 + 无新硬编码密钥 + 文档同步。
- 新增能力优先纳入 Spec-Kit：`.specify/specs/NNN-feature/` 建立 spec → plan → tasks → 验收。
