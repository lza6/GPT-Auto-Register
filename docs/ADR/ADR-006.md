# ADR-006: v3.0→v3.1 — 前端闭环 + settings 类型清源 + 浏览器池接入 + 默认安全的权衡

**状态**：已采纳（2026-08-06）
**关联**：`api/settings.py`、`api/proxies.py`、`api/__init__.py`、`services/browser_register.py`、`services/browser_pool.py`、`services/config_schema.py`、`web_dist/{index.html,app.js,app.css}`
**本次提交**：v3.1 前端闭环 + bug/技术债清理

## 背景

v3.0 已把大量能力落到后端（浏览器池框架 H3、config_schema 校验 P0、双引擎契约 B1、token 巡检 G1、代理健康 P2-4、失败分级 A4A6），但**前端 `app.js` 几乎未接入**，且审计发现若干 bug/技术债：

1. `api/proxies.py:/health` 的 `proxy_url` 被赋值两次，第一行三元表达式两分支都调 `_http_url`（残留无效代码，被紧随的 if/else 立即覆盖）。
2. `web_dist/` 从 700 行单文件拆为 `index.html`+`app.js`+`app.css` 后未收尾：`index.html` 的 `<style>` 空置、`app.css` 结尾残留 `</style>` 标签。
3. `services/browser_pool.py:acquire` 返回占位实例，但调用方 `browser_register.py` 完全未接入池（grep 零命中）——池化路径是死代码。
4. 版本号 `2.2.0` 与 v3.0 能力不符（3 处硬编码）。
5. **实证新增 P0**：`api/settings.py:ALLOWED_SETTINGS_KEYS` 白名单不含任何 v3.0 新键，前端保存会被 400。
6. **实证新增 P0**：`set_setting` 把所有值存为字符串，int 字段（如 `token_refresh_interval_sec`）经前端保存后 config.json 存 `"21600"`，`config_schema` 启动校验告警——前端保存反而制造脏数据。

## 决策

### 1. settings 写入「类型清源」，DB 与 config.json 分离处理

核心矛盾：DB `settings` 表是字符串 KV（`get_setting()` 返回 `str` 的契约被 `test_settings.py` 依赖），而 `config.json` 是启动真源、`config_schema.validate_config` 校验它。

**决策**：新增 `_coerce_value(key, value)`，仅对能可靠识别的值按 `_CONFIG_SCHEMA` 转类型——int 键收纯数字字符串转 int；bool 键收 `true/false/1/0/yes/on/...` 转布尔；无法识别的**原样返回**（交给 schema warn-only 提示，不静默吞、不静默转）。

写入路径分离：
- `set_setting(key, req.value)`：DB 仍存原始字符串（`get_setting` 契约不变，现有测试零改动）。
- `config[key] = _coerce_value(...)`：config.json 存正确类型，消除 schema 告警。

**为什么 DB 不一起转 int**：`get_setting()` 返回 str 是既有契约，运行时用 `_as_int`/`_as_bool` 兜底，转 int 会破坏 `test_settings.py:41` 的字符串断言且无益——脏数据的危害只在 config.json（schema 告警 + 启动误导）。DB 层保持字符串是无害的 KV。

### 2. 白名单扩容 4 个 v3.0 键

`ALLOWED_SETTINGS_KEYS` 追加 `browser_pool_size`/`token_refresh_enabled`/`token_refresh_interval_sec`/`cf_retry_max`。`auth_key` 仍严格排除（防配置注入覆盖鉴权密钥）。

### 3. 浏览器池接入 —— 代理按 context 隔离，browser 实例代理无关

关键设计澄清：本项目代理是在 `browser.new_context(proxy=...)` 按 **context** 设置的，**camoufox browser 实例本身代理无关**。因此池化复用 browser + 每账号新建 context **不会串 IP**（每个 context 携带各自代理）。

接入方式（`register_one`）：
- `browser_pool_size>0` 时 `pool.acquire(proxy_url)`，占位实例在**锁外**启动 camoufox 填充；复用实例直接拿来 `new_context`。
- `pooled_ok=True`（正常完成到 `context.close()`）才 `pool.release` 归还复用。
- 异常时**先关闭再标记为占位让 release 丢弃**——不复用可能损坏的实例（防坏实例在池内循环放大失败）。
- `browser_pool_size=0`（默认）走原冷启动，行为零变化。

**默认 `browser_pool_size=0` 不池化是正确默认**：尽管技术上按 context 隔离不串 IP，但 kookeey 动态住宅代理每账号本就独立 IP，池化收益主要在「固定通用 HTTP 代理」场景。前端高级设置项带醒目警告说明此边界。

### 4. token 巡检默认关闭

`token_refresh_enabled` 默认 `false`——避免与 chatgpt2api 的自动刷新职责冲突（重复刷新可能触发 OpenAI 限流/吊销 refresh_token）。巡检失败仅记 log + 跳过，**不删旧 token**（保留可用旧值）。前端 T2 仪表盘在未启用时显示启用指引而非报错。

### 5. 前端 700 行单文件拆三文件 + 一致性校验

拆分收尾：删除 `index.html` 空置 `<style>`、`app.css` 残留 `</style>`。用三重校验防「拆分漏迁 id/class」静默失效：
- `node --check app.js` 语法。
- `getElementById` 引用的 id 与 `index.html`/弹窗注入 id 双向比对。
- 真实无头浏览器（playwright python）加载点遍 5 个标签页 + 开高级弹窗，断言 **0 console error + 0 request failed**。

### 6. A4A6 失败自适应阈值（沿用 v3.0，本轮仅前端卡片化）

`server_5xx` 连续 3 次暂停 60s、风控占比 >40% 暂停——阈值沿用 v3.0 引擎实现不动。前端 T8 把 `last_task_failure_types` 渲染为分类徽章卡片（占比 + 一句话引导），替代原纯文本塞入。

## 验证

- `pytest tests/ -p no:warnings` → **253 全绿**（新增：settings 类型清源 6 + proxy health 2 + 池化集成 3 + healthz 版本/静态 2）。
- 真实 uvicorn 冒烟：`/api/healthz` 返回 `version:"3.1.0"`；`/api/stats/token-health` 禁用形态正确；`/api/proxies/health` 结构正确且 kookeey 行正确路由 `_kookeey_url`；`/`、`/app.js`、`/app.css` 全 200。
- 无头浏览器点遍标签页 + 高级弹窗：0 console error、0 request failed；token 卡片/4 个高级字段/代理健康列均渲染。
- `config_schema.validate_config(config.json)` 无告警（历史脏数据 `register_concurrency:"true"`/`register_interval_sec:"15"` 已清源为 int）。

## 诚实边界（未闭环，沉淀长尾）

- **T6 浏览器池复用**已真实冒烟（`scripts/smoke_browser_pool.py`，真实 camoufox）：同代理两次 acquire 复用同一真实实例（launch_count 恒为 1 不重启）、复用实例真实导航成功、cleanup 真实关进程。**未**验证的是完整 `register_one` 注册流（需真实 OpenAI 账号 + 代理，会遇到 CF/取码）。
- **T7 token 巡检**已真实端到端闭环（`scripts/smoke_token_refresh.py`）：用真实 OpenAI refresh_token（`data/export_chatgpt2api.json` 里 23 个其一）在临时库跑真实 `_scan_once`（不 mock）→ `{scanned:1, refreshed:1, failed:0}`，临时库 access_token 从占位更新为真实新 JWT。**本轮修复**：`_refresh_token` 原本不走代理（注册走代理、巡检不走会致「仅代理可达 OpenAI」部署永远失败）——已补 `_resolve_proxy`。**观察**：OpenAI 每次刷新返回新 refresh_token，但旧的在窗口期内仍可用（复用旧 token 仍 HTTP 200），故现设计只存 access_token 可接受；「同时落库最新 refresh_token」列为 v3.2 观察项（YAGNI，暂不预先实现）。
- **T3 代理健康**仅探测 TCP 端口可达（3s），**≠ 账号可用**（kookeey 动态住宅端口可达仍可能账密/国家码失效）。真实 HTTP 出口探测见 v3.2 前瞻。
- 代理池 500 条全量探测约 150s（并发 10 × 3s），属预期耗时，非 bug。
