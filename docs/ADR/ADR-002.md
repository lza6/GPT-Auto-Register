# ADR-002: 并发批量注册 + 暂停/停止语义

**状态**：已采纳（2026-08-05）
**关联**：`services/register_engine.py`

## 背景

批量注册初期串行 `for` 循环，100+ 账号耗时与并发无关，浪费多核与代理资源。`config.register_concurrency` 字段早已存在但未实现。

## 决策

`run_batch` 改为**信号量限流 + asyncio.gather** 并发执行：
- 并发度 = `register_concurrency`（默认 1，保持串行语义兼容）。
- 每账号独立 `register_one`（幂等），`Semaphore` 限制同时运行槽位数。
- `stats` 累加与 `update_task_progress` 用 `asyncio.Lock` 保护，避免进度错乱。
- **暂停**用 `asyncio.Event`（`pause()` clear，`resume()` set），替代 `while+sleep(1)` 空转。
- **停止**置 `_running=False` 并 set 事件，唤醒所有排队槽位检查后退出。
- 暂停检查放在 `async with sem` 内，确保"已排队但未开始"的账号也被暂停拦截。
- 断点续跑保持：`emails` 按 pending 驱动 + 预加载 success 集合去重（只查一次，O(N²)→O(1)）。

## 后果

- 正面：批量注册提速至接近 1/并发度；暂停/停止不丢进度、不重复注册。
- 正面：失败分类（`failure_types`）随 `tasks.result` 落库。
- 负面：并发下 `register_interval_sec` 语义变为"每槽完成后间隔"，总时长 ≈ 单号时长 × ceil(N/并发)。
- 负面：高并发可能触发 OpenAI 限流，需靠代理错开 IP（已由 kookeey 动态 IP 缓解）。

## 替代方案

- 多进程分片（WORKFLOW.md 早期做法）：需人工分片、难统一状态 —— 弃，改进程内协程并发。
- 线程池（`ThreadPoolExecutor`）：`register_one` 内部用 `run_in_executor`，外层再套线程会混乱 —— 弃。

## 验证

- 单测：并发槽位 ≤ 配置、默认并发=1、暂停阻塞/恢复继续、停止阻止剩余、无重复注册、失败分类落库。
