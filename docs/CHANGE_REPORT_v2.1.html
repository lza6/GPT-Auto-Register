1. 上下文与直觉

用户报告 refresh_all.py 批量刷新大量账号 180s 超时强杀。初始诊断写的是 input[name=email] 15s 超时，但代码考古发现：

  • 校准 诊断行号对不上当前代码——verify 等的是 current-password 20s，不是 email 15s
  • 根因 verify_account_login.py.run() 是孤儿旧代码：没复用 browser_register.py 已有的 detect_login_page/_resolve_cf 形态分流
  • 遇到 CF 挑战页或 OpenAI 改版页就裸等密码框 + 裸等 OAuth code，最坏撞 180s 强杀
  • 证据 refresh_batch.log 实测：行 1-24 成功，行 25+ 全 180s 超时——系统曾工作过，运行中出问题

2. 做了什么（诚实分层）

Phase 1: 修自己 4 个漏洞 P0 止血

  1. verify 截图静默吞错：原 try/except: pass 吞了"目录不存在"错误（违宪）。修：data/debug/ 用 mkdir(parents=True, exist_ok=True) 自动创建。
  2. 退出码契约断：verify 返回码 3/4 但 refresh_all.py 仍记 exit=1、reason 空。修：加 EXIT_NAMES 映射，rc=3→cf_blocked，rc=4→unknown_page。
  3. CF 重试资源泄漏：换代理时 new_context 抛异常会让 page 悬空、finally 二次 close 再抛。修：包进 try/except，失败 break 到 cf_blocked。
  4. token 回写静默丢失：_writeback_token 返回 False 时 verify 仍报 EXIT_SUCCESS。修：返回 False 则 EXIT_FAIL。

Phase 2: 核心链路 校准

校准发现：C2（去重 O(1)）+ D2（任务表落库）已在 v2.0 闭环（register_engine.py:164-165 预加载集合 + 每号 update_task_progress）。上次需求矩阵过时。本次无需重修。

Phase 3: 架构收敛（DRY） P2

6. 变更测验

以下测验必须通过，确认你理解本次变更：

Q1: verify_account_login.py 遇到 CF 挑战页时，现在返回什么退出码？
答：3 (EXIT_CF_BLOCKED)。refresh_all.py 据此记 reason=cf_blocked。
Q2: 遇到 unknown 页（无 email/password/code input），verify 返回什么码？截图落到哪？
答：4 (EXIT_UNKNOWN_PAGE)。截图落 data/debug/verify_unknown_*.png，目录不存在自动创建。
Q3: browser_register CF 重试时，new_context 抛异常会怎样？
答：try/except 捕获 → break 跳出循环 → 返回 cf_blocked。page 不悬空，避免 finally 二次 close 再抛。
Q4: _writeback_token 返回 False（数据库不可达）时，verify 返回什么？
答：EXIT_FAIL (1)。token 已获取但未持久化不再静默报成功。
Q5: OTP 提取三合一后，三个 email service 的行为和原来一致吗？兜底取第几个？
答：一致。font-24px > bg-F3F3F3 > max(所有非全同/非黑名单 6 位数字)。全同数字(111111)与地址邮编(90210等)排除。
Q6: C2 去重 O(1) 和 D2 任务表落库——本次新修的吗？
答：否。校准发现已在 v2.0 闭环（register_engine.py:164-165 预加载集合 + 每号 update_task_progress）。本次需求矩阵过时，无需重修。
Q7: verify 修复验证了真实 CF 页吗？为什么？
答：没有。无真实账号可跑，仅 mock 验证早退逻辑。真实 CF Turnstile 点不掉时仍需人工/换代理，但已明确标记 cf_blocked 不再卡 180s。这是诚实边界。
