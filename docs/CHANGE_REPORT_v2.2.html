M4: logs 表容量上限 P2

原 logs 表无硬上限（虽有 purge_old_logs 按天数清理，但单日高频爆量仍会撑大）。新增：

边界验证：MAX(id)=100、MAX_LOG_ROWS=20000 时 id <= -19990 永假删 0 条 ✓ 安全。

5. 变更测验

以下测验必须通过，确认你理解本次变更：

Q1: /api/healthz 现在返回哪些新字段？
答：db / cf_solver / browser_pool_size / version（cf_solver 用 socket connect_ex 探 8001 端口）。
Q2: get_stats 聚合 SQL 用什么方式替代 9 次 COUNT？返回结构变了吗？
答：1 条带子查询的 SELECT（每个字段是独立子查询 COUNT）。返回字段结构完全不变，前端无需改。
Q3: M4 的 MAX_LOG_ROWS 是多少？add_log 每次插入都清理吗？
答：20000。不是每次——每 100 次插入才检查一次，避免高频写入时 DELETE 子查询拖慢。
Q4: M4 边界：当 MAX(id)=100 但 MAX_LOG_ROWS=20000 时，DELETE 会删全表吗？
答：不会。WHERE id <= (100 - 20000) = id <= -19990，永假，删 0 条。安全。
Q5: B5 常量收敛后，protocol_register 的 REDIRECT_URI 和原值一致吗？旧 import 破坏吗？
答：一致。用 `from services.constants import OAUTH_REDIRECT_URI as REDIRECT_URI` 别名，旧 `from protocol_register import REDIRECT_URI` 不破坏。
Q6: D1 断点续跑为什么没在本轮新做？
答：校准发现 reset_stale_tasks 已在 v2.0 闭环（db.py:313 + main.py:44 调用）。不重复审计已修项是宪法要求。
