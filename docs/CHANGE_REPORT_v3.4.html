1. 项目概述和目标

GPT 自动注册项目是一个基于 curl_cffi + sentinel 风控参数的纯协议注册引擎，支持浏览器降级兜底，提供 Web 控制台进行批量注册管理。

v3.4 的核心目标：

  • 反风控升级：在已有「一账号一 IP」基础上，新增 TLS 指纹轮换 + UA 配套，实现「一账号一指纹一 IP」双隔离
  • 多平台扩展：邮箱库支持多平台标签，为后续 grok/claude 等平台自动化注册打地基
  • 生产级健壮性：日志异步批量落库消除写锁竞争、注册专用线程池消除并发钳制、主动告警通道
  • 自适应容错：代理黑名单自动拉黑风控出口、server_5xx 自适应暂停恢复、风控占比过高自动暂停

3. 每个变更的上下文和直觉

3.1 为什么需要一账号一指纹？

OpenAI/Cloudflare 风控不只看 IP，还看 TLS ClientHello 的 JA3/JA4 指纹 + HTTP/2 帧序。批量注册全用同一 Chrome 指纹会被聚类识别为"同一客户端在批量注册"。v3.2 已实现「一账号一 IP」（网络层隔离），但传输层指纹仍是同一种 Chrome，JA3 聚类可跨 IP 关联。

直觉：IP 隔离让风控无法从 IP 聚合，但 TLS 指纹相同等于告诉风控"这些请求来自同一客户端库"。指纹池轮换 + 每账号随机选一个 → 风控的 JA3 聚类失效。指纹与 UA 必须配套（Chrome 指纹配 Chrome UA、Firefox 指纹配 Firefox UA），否则矛盾反而更显眼。

线程安全：不在单例存可变指纹，_register_sync 局部生成贯穿全流程，多账号并发注册无竞态。

3.2 为什么需要多平台邮箱库？

项目目前只注册 ChatGPT，但同一套邮箱基础设施（微软邮箱接收验证码）可用于注册 grok/claude 等其他平台。需要：

  • 标记每个邮箱用于哪个平台（platform 字段）
  • 同一邮箱可在不同平台各注册一次（跨平台去重），同平台防重复
  • 前端可按平台筛选邮箱池

直觉：当前只做 schema 和 UI 地基，不引入 grok/claude 注册逻辑。平台切换按钮和统计已可用，但点"注册"时仍只注册 chatgpt — 后续版本集成新平台注册时，按 platform 区分即可。

3.3 为什么日志要改成异步批量？

原 add_log 每条独立 connect+PRAGMA+commit+close，单账号注册打 6-10 条日志，万级账号 = 8 万次完整连接生命周期抢同一 SQLite 写锁。与关键业务写（insert_account/update_task_progress）争 busy_timeout 导致"database is locked"。

直觉：日志不应该阻塞业务。队列 + 批量 flusher 让 add_log 变成 O(1) 内存操作，后台 200ms/200条一次 executemany 单事务落库。队列满时丢弃（计数可观测），绝不阻塞注册主链路。这是"日志是辅助设施，不是关键路径"的工程原则落地。

3.4 为什么需要专用线程池？

asyncio.run_in_executor(None) 走默认线程池 min(32, cpu_count+4)。register_concurrency=1 时信号量放行 1 个，但默认池资源被其他协程（token 巡检等）共享，OTP 同步 sleep 期间不会释放池线程，导致"并发度 1 也不够用"——新注册请求排队等池线程而非信号量。

直觉：注册专用池大小 = register_concurrency，确保"信号量放行即能拿到线程"。OTP 同步 sleep 在池线程内，不拖垮整批。硬超时护栏（asyncio.wait_for）防止 OTP 卡死永久占槽。

3.5 为什么需要告警通道？

批量注册是离线任务，用户不会一直盯着控制台。需要：

  • 批量完成通知（成功/失败数量）
  • 高失败率告警（>70% 自动推送）
  • 代理池耗尽、CF Solver 崩溃通知

直觉：webhook 兼容钉钉/企微/Bark，配置即用。异步 httpx 推送，失败仅记 log 不阻塞。5 分钟去抖防止重复告警轰炸。

3.6 为什么需要代理黑名单？

风控失败后同一出口代理继续被后续账号使用，100% 再次失败。kookeey 住宅代理每次 get_next 可能返回同一出口（取决于 session 随机性），固定代理列表更是一直重试同一批。

直觉：风控失败自动拉黑该代理 30 分钟，避免在同一死出口上重复浪费账号。持久化到文件，进程重启不丢失。黑名单 TTL 到期后自动恢复（代理可能已解封）。

4. 关键代码改动说明

4.1 TLS 指纹池核心（services/constants.py）

TLS_FINGERPRINT_POOL = ( "chrome120", "chrome123", "chrome124", "chrome131", "chrome133a", "chrome136", "chrome142", "chrome145", "chrome146", ) def pick_fingerprint(config: dict) -> str: """按配置选 TLS 指纹（一账号一指纹的入口）。 - config.tls_fingerprint 固定单个指纹（调试用，空=池内随机） - config.tls_fingerprint_pool 自定义池（逗号分隔，空=默认 Chrome 池） - 非法值回退默认池随机 """ def ua_for_fingerprint(fingerprint: str) -> str: """按 TLS 指纹产出配套的 User-Agent。 chrome123 → Chrome/123 UA；firefox135 → Firefox/135 UA 版本号从指纹名解析（chrome123→123；safari180→18.0 取 18） """

设计要点：

  • 默认池只放 Chrome 各版本（行为最接近现状，最保守）
  • Firefox/Safari 作为可选池（tls_fingerprint_pool 显式配置才混入）
  • UA 跟随指纹族（chrome/firefox/safari/edge 各族配套），用户显式配 user_agent 时优先（向后兼容）
  • curl_cffi 0.16.0 实测可用

4.2 协议注册接入指纹（services/protocol_register.py）

def _fresh_fingerprint(self) -> tuple[str, str]: """为一次注册生成 (TLS指纹, 配套UA)。每账号调用一次 → 一账号一指纹。""" fp = pick_fingerprint(self.config) if str(self.config.get("user_agent") or "").strip(): return fp, self.ua return fp, ua_for_fingerprint(fp) # 在 _register_sync 开头： fingerprint, fp_ua = self._fresh_fingerprint() # 贯穿全流程： session = self._make_session(proxy_url, fingerprint) # 建会话用指纹 # authorize 用 fp_ua # 所有 API 请求用 fp_ua # _exchange_code 用 fingerprint + fp_ua

设计要点：

  • 指纹和 UA 在 _register_sync 开头生成一次，贯穿全流程（authorize/取码/换 token 同一指纹同一 UA）
  • 不同账号 = 不同 _register_sync 调用 = 不同指纹（线程安全，无竞态）
  • _make_session 用本账号选定的 TLS 指纹（非固定 chrome），curl_cffi 的 impersonate 参数支持

4.4 日志异步批量落库（services/db.py）

_LOG_QUEUE: queue.Queue = queue.Queue(maxsize=5000) _LOG_FLUSH_BATCH = 200 _LOG_FLUSH_INTERVAL = 0.2 def _log_flusher(stop): """后台线程：批量把日志队列落库，executemany 单事务，降写放大。""" while not stop.is_set(): batch = [] # 阻塞等第一条（带超时实现周期 flush） first = _LOG_QUEUE.get(timeout=_LOG_FLUSH_INTERVAL) batch.append(first) # 非阻塞抓满一批 while len(batch) < _LOG_FLUSH_BATCH: try: batch.append(_LOG_QUEUE.get_nowait()) except queue.Empty: break if batch: _write_log_batch(batch) # executemany 单事务 def add_log(level, message, data=None): """v3.4 异步批量：仅入内存队列，由后台 flusher 批量落库。 队列满（突发洪峰）时丢弃并计数，绝不阻塞注册主链路。""" payload = (level, message, json.dumps(data) if data else None, time.time()) try: _LOG_QUEUE.put_nowait(payload) except queue.Full: _log_dropped["n"] += 1 # 可观测丢弃计数

设计要点：

  • add_log 从 1 次 connect+PRAGMA+commit+close 变成 1 次 put_nowait
  • 队列满时丢弃计数，绝不阻塞业务（可观测：_log_dropped["n"]）
  • get_logs 读取前 flush 保证最新日志可见
  • atexit 注册 stop_log_flusher 进程退出排空
  • flusher 守护线程，进程退出随主线程结束

4.5 代理黑名单（services/proxy_service.py）

def mark_bad(self, proxy_url: str, reason: str = "risk_control", ttl_sec: int = 1800) -> None: """把代理加入黑名单，TTL 内不再被 get_next/get_random 取到。""" # 从 proxy_url 反查 proxies.txt 行（反向匹配 host:port） u = urlparse(proxy_url) target = f"{u.hostname}:{u.port}" if u.port else u.hostname # 匹配最接近的行 line = proxy_url for entry in self._entries: if target in entry["line"] or proxy_url in entry["line"]: line = entry["line"] break self._blacklist[line] = {"expires_at": time.time() + ttl_sec, "reason": reason} self._save_blacklist() # 持久化到文件

设计要点：

  • mark_bad 从 proxy_url 反查 proxies.txt 行（反向匹配 host:port）
  • 持久化到 data/proxy_blacklist.json（进程重启不丢失）
  • get_next/get_random 跳过黑名单内未到期代理
  • 黑名单到期后自动恢复，无需手动清理
  • register_engine 中 risk_control 失败自动调用 mark_bad(ttl=1800s)

6. 剩余风险和边界

  • 多平台注册仅 schema 就绪：platform 字段和 platform_usage 表已完备，但注册逻辑仍只针对 chatgpt。切换平台后点"开始注册"仍注册 chatgpt——需要后续版本按 platform 分发注册逻辑。
  • 代理黑名单粒度：kookeey 动态住宅每次 get_next 生成随机 session → 新 IP。mark_bad 标记的是 proxies.txt 某行而非具体 IP，因此该行下所有 session 都会被屏蔽 30 分钟。可接受（kookeey 行对应一个住宅出口段）。
  • 异步日志丢弃不可恢复：队列满时丢弃的日志仅计数，无法事后捞回。生产部署建议调大 maxsize 或确认日志洪峰不会超过 5000 条 backlog。
  • 告警配置需手动写入 config.json：notify_webhook_url/notify_events 仅在 config.json 中读取，settings API 尚未提供前端配置入口。
  • 指纹池仅 Chrome 族：默认池只放 Chrome 各版本；Firefox/Safari/Edge 需要 tls_fingerprint_pool 显式配置才混入——保守策略，但可能不够多样。
  • curl_cffi 版本依赖：TLS 指纹模拟依赖 curl_cffi 0.16.0+ 的 impersonate。若项目使用的 curl_cffi 版本较旧，部分指纹可能不可用（回退到 chrome 默认）。

7. 变更测验（15 题，必须通过）

以下测验确认你理解 v3.4 全部变更。每道题先自己思考再核对答案。

Q1 [选择]一账号一指纹的核心目的是什么？
A. 让每个账号使用不同的浏览器渲染引擎
B. 防止 JA3 聚类识别批量注册，在传输层隔离各账号
C. 加快注册速度
D. 兼容更多代理类型
正确答案：B。JA3/JA4 指纹是 TLS ClientHello 的特征值，同一指纹可跨 IP 关联。每账号不同指纹 = 风控无法从 TLS 层聚类。
A 错：curl_cffi 的 impersonate 只改 TLS 指纹，不改渲染引擎。C 错：指纹轮换不改变注册速度。D 错：与代理类型无关。
Q2 [选择]指纹和 User-Agent 的关系是什么？
A. 指纹和 UA 可以各自独立随机选择
B. 指纹和 UA 必须配套（Chrome 指纹配 Chrome UA），否则矛盾反而更显眼
C. UA 由指纹自动生成，用户不可干预
D. 指纹自动跟随 UA 变化
正确答案：B。Chrome 指纹配 Firefox UA 等于告诉风控"我在伪装"。配套原则：指纹族决定 UA 族，版本号从指纹名解析。用户显式配置 user_agent 时优先（向后兼容）。
C 错：用户可设 user_agent 覆盖。D 错：指纹独立选择，UA 跟随而非反过来。
Q3 [判断]默认 TLS 指纹池包含 Chrome、Firefox、Safari 三种浏览器。
错误。默认池只放 Chrome 各版本（chrome120/123/124/131/133a/136/142/145/146）。Firefox/Safari 需要 tls_fingerprint_pool 显式配置才混入——保守策略，Chrome 行为最接近现状。
Q4 [选择]多平台邮箱库中，(email, platform) 唯一约束的作用是什么？
A. 限制每个邮箱只能注册一个平台
B. 同邮箱同平台只记一次使用，不同平台可各注册一次
C. 防止邮箱重复导入
D. 限制每个平台只能使用一个邮箱
正确答案：B。UNIQUE(email, platform) 确保同一邮箱在 chatgpt 平台只注册一次，但可以在 grok 平台再注册一次（跨平台去重）。
A 错：一个邮箱可在不同平台各注册一次。C 错：不防邮箱重复导入（emails 表本身 email UNIQUE）。D 错：不限平台使用邮箱数量。
Q5 [判断]platform_usage 表在插入邮箱时自动创建一行 pending 记录。
正确。insert_email() 内部同时调用 INSERT OR IGNORE INTO platform_usage (email, platform, status) VALUES (..., 'pending')。注册成功后 mark_platform_usage 更新为 used。
Q6 [选择]日志异步批量落库的最大好处是什么？
A. 减少日志文件大小
B. 消除 add_log 与关键业务写的 SQLite 写锁竞争
C. 提高日志可读性
D. 加快日志查询速度
正确答案：B。原 add_log 每条独立连接+提交，万级账号 = 8 万次完整连接生命周期，与 insert_account/update_task_progress 争 busy_timeout 导致"database is locked"。改为队列后 add_log 是 O(1) 内存操作。
Q7 [判断]日志队列满时，新日志会阻塞主线程直到队列有空间。
错误。put_nowait 满时抛出 queue.Full 异常，被捕获后丢弃日志并计数（_log_dropped["n"] += 1）。绝不阻塞注册主链路——日志是辅助设施，不是关键路径。
Q8 [选择]为什么需要注册专用线程池？
A. 为了增加并发注册数
B. 确保信号量放行即能拿到线程，OTP 同步 sleep 不拖垮整批
C. 为了减少内存占用
D. 为了兼容 Python 3.12
正确答案：B。默认池 min(32, cpu+4) 被其他协程共享，池线程满时新注册请求排队等线程而非信号量——并发度形同虚设。专用池大小 = register_concurrency，信号量放行即能拿到线程。
Q9 [判断]register_one 的硬超时护栏使用 asyncio.wait_for，超时后 OTP 同步线程立即被终止。
错误。asyncio.wait_for 只取消协程，executor 里的同步线程会继续跑完。但 asyncio 槽位及时释放、进度不错乱。超时原因按 otp_timeout 落库。
Q10 [选择]_auto_resume_handle 改为实例属性 + 批次代数校验解决了什么问题？
A. 内存泄漏
B. stop 后 60s 自动恢复任务仍"复活"，跨批次串扰
C. 恢复速度太慢
D. 暂停后无法恢复
正确答案：B。原为局部变量，stop 后 60s 自动恢复任务仍执行 resume() 导致"死而复生"；新批次启动时旧批次恢复任务串扰。改为实例属性后 stop() 可 cancel()，批次代数校验让旧批次恢复任务放弃执行。
Q11 [判断]主动告警通道使用同步 requests 发送 webhook。
错误。使用异步 httpx.AsyncClient，失败仅记 log 不阻塞注册主链路。5 分钟去抖防止重复告警。
Q12 [选择]代理黑名单中，mark_bad 标记的粒度是什么？
A. 具体 IP 地址
B. proxies.txt 的某一行
C. 整个代理文件
D. 当前 session
正确答案：B。mark_bad 从 proxy_url 反查 proxies.txt 行（反向匹配 host:port），标记该行。kookeey 动态住宅一行对应一个出口段，黑名单 TTL 30 分钟后自动恢复。
Q13 [判断]代理黑名单持久化到 data/proxy_blacklist.json，进程重启后黑名单丢失。
错误。_load_blacklist 在初始化时从文件加载，只加载未过期的黑名单项。进程重启不丢失。
Q14 [选择]以下哪个模块在 v3.4 中首次引入？
A. protocol_register
B. config_schema
C. notifier（主动告警）
D. proxy_service
正确答案：C。services/notifier.py 是 v3.4 全新模块，提供 webhook 告警推送。其他三个在 v3.1/v3.2 已存在。
Q15 [判断]多平台邮箱库的前端平台切换按钮，切换后"开始注册"会自动注册对应平台。
错误。前端平台切换和过滤已完备，但 run_batch 的注册逻辑仍只针对 chatgpt。切换平台后点"开始注册"仍注册 chatgpt——需要后续版本按 platform 分发注册逻辑。当前只完成了 schema 和 UI 地基。
