1. 上下文与直觉

v3.1 发布后，用户要求一次最严格的终局闭环总审计：把整个项目当作"即将被真实用户/调用方/部署者使用"的产品，全面查漏补缺。本轮用 7 维并行子代理审计（API契约/前端UI/后端逻辑/数据SQL/配置部署/安全/文档一致性）产出 80 条原始发现，再对 P0/P1 做对抗验证（怀疑者逐条反驳），最后用批判性审查线程（有罪推定/零容忍）复审修复并循环复验。

2. 最强自我反驳（先攻击自己）

  • "协议注册一直很正常"是错觉：PKCE verifier/challenge 错配导致换 token 必失败，但 fallback_browser 让浏览器兜底成功，表面看"协议优先"在正常跑。mock 测试 mock 了 _exchange_code，从没测到真实配对。→ 实证 sha256(verifier)!=challenge，确认 P0。
  • "token 巡检已闭环"其实埋了耗尽雷：v3.1 记忆写"旧 RT 窗口期不作废"，本轮实测发现那是窗口期前 1-2 次；用 2-3 次后 OpenAI 返回 401 refresh_token_reused。token_refresher 只存 access_token 会让库存 RT 逐步耗尽。→ 真实账号实测确认，升级为 P0/P1 修复。
  • "README 说前端填 auth_key"是伪功能：前端全文无 X-Auth-Key 机制，开鉴权后 Web 控制台全 401 变砖。→ 补 401 弹窗收集 + playwright 实测。
  • "bat 读 config 端口"第一版是伪修复：for /f 解析 python 时遇 `)` 提前闭合，静默失败。批判审查员抓到，改用 set /p 实测通过。→ 我自己引入了伪落地，被复审抓获。
  • "root logger 设 DEBUG 是善举"实则泄密：httpx DEBUG 会把携带 refresh_token/密码的请求头+body 写进 server.log。→ 复审抓获，改 root=INFO + 压 httpx。

5. 剩余真实风险与边界（诚实）

  • P0 待用户决策：生产实例当前无鉴权裸奔（config.json auth_key 占位符 + auth_enforced=false + host=0.0.0.0）。代码已有 fail-fast 机制，这是部署决策——需用户设真实 auth_key + auth_enforced=true。已在本报告与 README 显著标注。
  • PKCE/RT 轮换修复经真实 token 验证，但未跑完整真实注册流（需真实 OpenAI 账号+代理遇 CF/取码），协议注册端到端成功率的提升幅度需生产观察。
  • 代理健康仅 TCP 可达 ≠ 账号可用；真实 HTTP 出口探测列 v3.2。
  • settings 保存后运行时不生效（get_engine 单例缓存 config）需重启——已诚实标注，P2 长尾。
  • 实测用掉 2 个真实账号的 RT 链（dbf/xww）做验证——RT 已轮换，这 2 个账号的旧 RT 失效属预期。

6. 本轮不适用的项（说明而非忽略）

  • 高并发基础设施（Load Balancer/Redis/Kafka/Sharding/消息队列/熔断）：本项目是单机注册工具，非多租户高并发 SaaS，引入这些属过度工程（违 YAGNI + 宪法增量迭代）。已具备的是：Semaphore 并发限流、SQLite WAL、连接管理、健康检查、日志容量上限。
  • CDN/数据库复制：单文件 SQLite + 本地静态前端，无此需求。

7. 变更测验

以下测验必须通过，确认你理解本次终局审计：

Q1: protocol_register 的 PKCE bug 是什么？为什么多年没被发现？怎么修的？
_build_authorize_url 与 _register_sync 各自调用 _gen_pkce() 生成不同对，authorize 上报的 challenge 与换 token 用的 verifier 不配对（sha256(verifier)!=challenge），OpenAI 换 token 必失败。没被发现因为：①测试 mock 了 _exchange_code 从没测真实配对；②fallback_browser 让浏览器兜底成功掩盖。修法：_register_sync 生成同一对 verifier+challenge，challenge 传入 _build_authorize_url，verifier 传 _exchange_code。
Q2: OpenAI refresh_token 轮换有什么坑？token_refresher 原来的 bug 是什么？
OpenAI 每次刷新返回新 refresh_token，且旧 RT 重用 2-3 次后返回 401 refresh_token_reused 作废。原 token_refresher 只存 access_token、丢弃新 RT，导致库存 RT 逐步落后直至耗尽失效。修复：_refresh_token 返回完整三件套，_update_tokens 同时落库新 access_token 和新 refresh_token。导出路径同样补 _writeback_rotated_tokens。
Q3: 为什么"README 说前端设置页填 auth_key"曾被称为伪功能？怎么修的？
前端 app.js 的 api() 只设 Content-Type、全文无 X-Auth-Key 注入、index.html 无密钥输入框——开鉴权后 Web 控制台所有 /api/* 立即 401 变砖，与 README 宣称矛盾。修复：api() 从 localStorage 读密钥注入 X-Auth-Key，收到 401 弹窗收集一次并重试，密钥错误自动清除。
Q4: 我把 register_interval_sec 的 sleep 从 sem 外移入 sem 内，为什么？原来在 sem 外有什么问题？
sem 外时协程先释放信号量再 sleep，排队的下一个协程立即获得槽位启动注册——任意并发度（含 concurrency=1）下相邻注册启动间隔≈0，限速配置完全失效。移入 sem 内后槽位持有信号量走 interval，才真正间隔下一次启动。另补分段 sleep（0.5s 粒度查 _running）让 stop 在 interval 期间也能及时响应。
Q5: 改 .bat 读 config.json 端口时，for /f 为什么会静默失败？正确做法是什么？
for /f 用 ( ) 作命令串分隔符，python 代码里的 )（如 open(...) / print(...)）会提前闭合 for 命令串导致静默失败（2^>nul 吞掉错误）——与单引号/中文路径无关。正确做法：python 把端口直写临时文件，用 set /p VAR= Q6: root logger 为什么不能设为 DEBUG？正确的日志级别策略是什么？
root 设 DEBUG 会让 httpx/asyncio/playwright 输出 DEBUG，其中 httpx DEBUG 打印完整请求头和 body——本项目出站请求携带 refresh_token/邮箱密码/OAuth code，等于把机密明文写进 server.log。正确：仅业务 logger gpt-register 设 DEBUG，root 保持 INFO，并显式压 httpx/httpcore/urllib3/playwright/asyncio 到 WARNING。
Q7: 本轮 TLS verify=False 为什么能安全改成 verify=True？万一某部署的代理做 SSL 拦截怎么办？
实测 verify=True 经代理可用（httpx 403/curl_cffi 200 都说明证书校验通过）——CONNECT 隧道代理（kookeey/v2ray）不中断端到端 TLS，当初设 False 是过度谨慎。若部署代理做 SSL 拦截导致证书错误，设 config.tls_verify=false 回退（config_schema 已留位，默认 true）。
