## 二、健康度诊断（代码考古结论）

> 以下全部基于对当前代码的逐文件阅读得出的**根因分析**，非猜测。每条含：位置、根因、影响、修复方向。

### 🔴 CRITICAL（必须优先修复）

#### C1. 注册链路当前实际失败（正在发生）
- **位置**：`scripts/verify_account_login.py:131-133`；同样逻辑在 `services/browser_register.py:177-189`；根因诊断脚本 `authorize_diag.py`
- **现象**（`verify_out.txt` 实测输出）：`Locator.wait_for: Timeout 15000ms exceeded. waiting for locator("input[name=email]")`，最终停在「访问 authorize URL」后没有任何可见 input
- **根因分析**：
  1. `page.goto(authorize_url, wait_until="networkidle", timeout=60000)` + `sleep(5)` 后依然无邮箱框，说明**页面未成功渲染**，可能原因：a) 当前代理出口被 CF 拦截，卡在 Turnstile/检查页；b) OpenAI 登录页改版（input 结构变化）；c) 该邮箱被风控需要走「密码登录」而非「邮箱注册页」
  2. `browser_register.py` 只识别 `input[name="email"]` 单一形态，一旦页面是密码登录页 / CF 检查页 / 错误页，直接判定失败
- **影响**：**整个注册功能当前不可用**，属于必须止血的 P0
- **修复方向**：见 [模块 A](#模块-a注册链路稳定性最高优先级)

#### C2. 控制台无鉴权（auth_key 形同虚设）+ CORS 配置错误
- **位置**：`config.example.json:2`（`auth_key` 字段）；`api/__init__.py:30-36`
- **根因**：`auth_key` 仅在配置里声明，代码中**零引用**；任何能访问 `http://<host>:23457` 的人都可以「一键清空库」「导出全部账号密码」「查看日志」
- **CORS 配置错误**：`allow_origins=["*"]` 与 `allow_credentials=True` 同时存在，按规范浏览器会拒绝携带凭据的跨域请求（且 `*` 本身不安全）
- **修复方向**：见 [模块 E](#模块-e安全加固)

#### C3. tasks 任务表从不更新（状态永久失真）
- **位置**：`api/register.py:72-80`（插入 running）→ `services/register_engine.py:276-355`（run_batch **从不 UPDATE tasks**）
- **根因**：`INSERT INTO tasks` 后，`completed/failed/skipped/status/result` 从未写回；若服务中途退出，任务永远停在 `running`
- **影响**：前端「进度条」无法展示真实进度；无法断点续跑；任务历史不可信
- **修复方向**：见 [模块 D-D2](#d2任务状态实时落库)

### 🟠 HIGH（严重影响体验与可维护性）

#### H1. register_engine 的 curl_cffi 纯协议注册是死代码（且具误导性）
- **位置**：`services/register_engine.py:60-251`（`_register_sync`、`_make_session`）
- **根因**：`WORKFLOW.md` 第 43-44 行已明确「纯协议过不了 create_account，必须真实浏览器/前端 sentinel」；但 `register_one` 的 `use_browser=False` 分支仍保留这套 curl_cffi 流程，实际注册必然失败
- **影响**：误导后续维护者；若误配置关闭浏览器方式，整批失败且难以定位
- **修复方向**：删除死代码或改为显式抛错；见 [模块 B-B2](#b2清理死代码与残留)

#### H2. 双注册引擎逻辑漂移（DRY 破坏）
- **位置**：Web 引擎 `services/browser_register.py` vs 批量引擎 `scripts/revive_import.py`
- **根因**：同一套 OAuth PKCE + OTP + about-you + 换 token 流程在两处各写一遍，且已漂移：
  - 姓名生成：Web 用 `name_service`（`名字+姓+数字后缀`，如 `jamesmith123`），批量脚本用**纯字母随机**（`services/name_service.py:47-62` vs `scripts/revive_import.py:348`）
  - 年龄：Web 用生日算年龄，批量脚本直接随机 19-40（`browser_register.py:341` vs `revive_import.py:349`）
  - 登录页分支：批量脚本有 `log-in`（已知密码登录）与「邮箱验证码登录」分支（`revive_import.py:416-451`），Web 引擎**完全没有**，半成品账号无法继续
- **影响**：同功能两套行为，维护成本翻倍、行为不一致、修一处漏一处
- **修复方向**：见 [模块 B-B1](#b1统一注册协议为单引擎策略模式)

#### H3. 浏览器实例每号启停，无复用（速度与稳定性双输）
- **位置**：`services/browser_register.py:131-137`（每次 `AsyncCamoufox()` + `start()`）与 `:448-458`（每次 `close`/`stop`）
- **根因**：冷启动一个 camoufox 浏览器约 3-10 秒，还要下载/解压 profile；100 号就是 100 次冷启动
- **影响**：单号耗时大、CPU/内存反复波动、稳定性差（频繁启停易残留僵尸进程）
- **修复方向**：浏览器/上下文池复用；见 [模块 C-C1](#c1浏览器池复用)

#### H4. 去重判断 O(N²) 全表扫描
- **位置**：`services/register_engine.py:291-296`（`run_batch` 循环内每次 `get_accounts(status="success")` 全表查询）
- **根因**：去重集合应在循环外一次性加载，却放进了每个账号的循环体
- **影响**：100 号 → 100 次全表查询；账号越多越慢
- **修复方向**：循环外预加载 `set(email)`；见 [模块 C-C2](#c2批量循环去重优化)

#### H5. 前端「高级设置」把整个 config.json 明文暴露
- **位置**：`web_dist/index.html:687-699`（`openAdvanced()` 遍历 `Object.entries(cfg)` 渲染全部键值）
- **根因**：`api/settings.py:41-45` 的 `/settings/config` 直接返回完整 config，含 `auth_key`、`chatgpt2api_admin_key` 等
- **影响**：任何人打开高级设置即可看到管理密钥 → 与 C2 叠加，等于密钥公开
- **修复方向**：前端脱敏 + 后端按白名单返回；见 [模块 E-E2](#e2前端与接口密钥脱敏)

#### H6. 注册流程完全未接入 CF Solver
- **位置**：`services/cf_solver_service.py` 已实现完整的 `/clearance`、`/turnstile` 封装，但 `browser_register.py` **零引用**
- **根因**：CF Solver 服务会随 `启动.bat` 启动（`:8001`），但注册引擎遇到 CF 挑战时没有任何检测与调用
- **影响**：一旦代理出口被 CF 拦截（正是 C1 的可能原因之一），注册直接失败，兜底能力闲置
- **修复方向**：CF 检测 + 自动调用 Solver 重试；见 [模块 A-A3](#a3cf-检测与solver集成)

#### H7. 导出/推送账号时 token 刷新全串行、慢且失败无标记
- **位置**：`api/register.py:201-224`（`_collect_export_accounts` 对每个账号 `_refresh_oauth` 同步串行，单个 `timeout=60`）
- **根因**：N 个账号串行刷新，N=100 时最坏 100×60s；且刷新失败的账号没有任何记录/标记，用户无法知道哪些失效
- **影响**：导出按钮「卡死感」明显；失效 token 静默丢失
- **修复方向**：并发刷新（限流）+ 失败标记；见 [模块 C-C3](#c3导出并发刷新token)

### 模块 A：注册链路稳定性（最高优先级）

#### A1. 修复 authorize 页面识别（对应 C1）

**现状**：`browser_register.py:177-189` 只等 `input[name="email"]`，超时 15s 后仅换个选择器再等 10s，仍失败即截图退出。

**根因**：OpenAI 登录页至少有三种形态，当前只覆盖一种：
1. **邮箱输入页**（新账号注册，`screen_hint=login_or_signup` 下的默认页）
2. **密码登录页**（已有账号，需点「Log in with a one-time code」切验证码）
3. **CF 挑战页 / 错误页**（卡 Turnstile、检查浏览器等）

**目标方案**：写一个 `_detect_login_page(page)` 函数，按以下优先级识别并分流：

```python
# 伪代码——实现时放到 browser_register.py 或抽到 services/login_page.py
async def detect_login_page(page) -> str:
    """返回 'email' | 'password' | 'otp' | 'cf' | 'about-you' | 'callback' | 'unknown'"""
    url = page.url
    if "about-you" in url: return "about-you"
    if "auth/callback" in url and "code=" in url: return "callback"
    if is_cf_challenge(page): return "cf"
    for sel in [('input[name="email"]', 'email'),
                ('input[name="current-password"]', 'password'),
                ('input[autocomplete="one-time-code"]', 'otp'),
```

#### A4. 失败分级与重试策略（防限流 + 容忍抖动）

**现状**：`register_engine.py` 对失败不做分级，浏览器异常直接 failed；`revive_import.py` 只对 `Timeout` 重试一次。

**根因**：`WORKFLOW.md` 已强调 `email-otp/validate` 有 `max_check_attempts`，**绝不重试验证码提交**；但网络抖动、页面加载超时属于可重试类。

**目标方案**：失败原因分级 → 不同处置：
| 失败类型 | 示例 | 处置 |
|---------|------|------|
| 可重试（网络/超时） | `TimeoutError`、`ConnectionError`、goto 超时 | 最多重试 1 次，间隔 5s |
| 不可重试（业务） | OTP 提交 429/限流、`registration_disallowed`、`account_deactivated` | 立即弃号，写 skip 清单 |
| 账号级风控 | `deleted or deactivated` 403 | 记 `dead`，加入 skip，不再碰该号 |

**具体改动**：
- `services/register_engine.py` `run_batch` 内：捕获异常后先分类再决策；重试用独立计数 `attempt <= 2`
- 参照 `revive_import.py:594-616` 的 DeactivatedError 处理，把「停用号」写 `scripts/revive_skip.txt`（与批量脚本共用），避免 Web 与批量互相踩号

**验收标准**：模拟网络抖动（临时断网 3s）不导致整批失败；限流类错误不会重复触发。

**优先级**：P0 | **预估**：0.5-1 天

#### A5. 浏览器实例池复用

**现状**：每号 `AsyncCamoufox().start()` 再 `stop()`（`browser_register.py:131-137, 448-458`）。

**根因**：冷启动耗时 + 内存波动 + 僵尸进程风险。

**目标方案**：实现一个轻量 `CamoufoxPool`：
- 预热 1-2 个浏览器实例，空闲复用；每号从池中取 context（隔离代理、隔离 cookie）
- 控制最大实例数（`MAX_INSTANCES = 3`），避免内存爆炸
- `register_one` 结束后归还 context 而非关浏览器；进程退出时优雅关闭（`main.py` 挂 uvicorn shutdown 事件）
- 会话隔离注意：**同代理、同账号必须用独立 context**，避免串 cookie

**验收标准**：100 号注册不再每号冷启；任务管理器观察浏览器进程数恒定在 2-4 个；单号耗时下降 ≥30%。

**优先级**：P1 | **预估**：1-2 天

## 七、风险与注意事项

### 7.1 上游风险（不可控）
- **OpenAI 登录页/API 随时可能改版** → 缓解：A1 的 `unknown` 分支 + body 摘要日志，让适配时间从「排查数天」缩到「改一处」
- **邮箱验证码限流**（`email-otp/validate` max_check_attempts）→ 严格遵守「只提交一次」，任何重试策略不得触碰 OTP 提交
- **账号风控**：姓名带数字后缀、纯字母随机名都可能被判定异常 → 建议 L3 换更自然姓名池
- **代理出口被 CF 高频拦截** → 接入 A3 CF Solver 兜底；代理质量差时优先换源

### 7.2 数据安全
- 账号密码、refresh_token 均为**长期敏感凭证** → 鉴权（E1）落地前勿部署到公网；日志/截图不要打印完整 token
- `_refresh_oauth` 等 `httpx` 调用使用 `verify=False`（`browser_register.py:485` 等）→ 记录为已知项，不建议贸然开启验证（可能被中间人拦），但要在文档标注
- 前端显示密码默认掩码（已有），勿改为默认明文

### 7.3 改造原则（防止改乱）
- **只清理自己造成的混乱**：死代码可删（B2），正常工作的逻辑不重构
- **每步可回滚**：改前 `git`，分批提交；涉及数据库 schema 变更用迁移（`db.py:89-94` 已有 ALTER 迁移范例）
- **双引擎合并（B1）务必先写测试再合并**，避免行为漂移
- `register_engine.py` 的 curl_cffi 分支删除前确认 `use_browser` 在 config 中恒为默认 True，否则配置了 False 的用户会「注册必失败」且无明确提示

### 7.4 遗留待确认项（实施前与用户对齐）
1. 控制台鉴权方案选「极简 key」（推荐，快）还是「登录会话」？
2. 是否接入 IMAP 作为第三取码通道（需 `imapclient` 依赖）？
3. `scripts/旧版实验/` 与根目录诊断文件是**归档**还是**删除**？
